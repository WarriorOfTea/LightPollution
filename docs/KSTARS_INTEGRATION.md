# Интеграция в KStars
> Дата создания: 2026-11-11

Я встраиваю интерфейс в настоящий KStars как C++/Qt `QDockWidget`.
Физический расчёт работает в отдельном локальном Python-процессе; карта
остаётся отзывчивой. Web — другой клиент того же ядра, не способ
встроить панель. Исходники: [integrations/kstars](../integrations/kstars/).

## 1. Что я переиспользую

| Возможность KStars | Фактическое применение |
|---|---|
| GeoLocation/SimClock/SkyMap | Атомарные место, виртуальный UTC и направление центра |
| SkyPoint | Геометрические az/alt; рефракция повторно не вводится |
| StarComponent/DeepStarComponent | Установленные каталоги, JIT-позиции, V/B−V и HD для камеры |
| ArtificialHorizon | Все включённые контуры, потолки, проверки пикселей/звёзд |
| FITS Viewer | Открытие линейного синтетического FITS, stretch/zoom/гистограмма |
| XML camera-data Ekos | Частичный перенос pitch и RN выбранного режима/gain |
| OptimalSubExposureCalculator Ekos | Штатный расчёт из b в e⁻/pixel/s и того же RN, без SQM-прокси |

Ekos уже учитывает фон, QE, размер пикселя и RN; INDI CCD Simulator уже
имеет sky-glow, шум и дефекты. Моё добавление — направленная физическая
сцена и электронный фон по полю. Я не выдаю существующие функции за новые.
TerrainComponent с панорамой не заменяет метрический DSM двух путей света.

## 2. Управление панелью

В панели выбираю период, DSM, AGL, AOD, ближние площадки и спектр;
включаю глаз/экспериментальный цвет либо камеру. У камеры доступны
выдержка/фокусное/апертура, JSON-профиль и частичный XML-импорт Ekos.
Остальные настройки сохраняются при открытии полного `scene.json`.

При расчёте камера запрашивает звёзды доV12 в поле с запасом. Установщик
подключает Tycho-2 и современный базовый каталог с исправленными эпохами.
Запрос не доказывает полноту; в результате сохраняю максимум полученной V,
число записей/цветов, флаг обрезки и SHA-256 реально найденных файлов.
Точные повторения записи в соседних HTM-ячейках исключаю; разные компоненты
не сливаю по одному HD или угловому расстоянию.

В прежнем опыте было311 записей доV8 и188 центров в поле. Три близкие пары
проверены: старая эпоха одной записи сдвигала её относительно другой,
современные данные оставляют по одной согласованной записи.
[Исходные позиции и движения](../artifacts/kstars-catalogue-integration-20261112/three-pairs-audit.json).
Обоснование очистки и B−V — [MODELS](../MODELS.md#подготовка-глубокого-каталога-и-cross-id).

Результат глаза открываю отдельным Qt-окном; FITS камеры — штатным
FITS Viewer с проверяемым сигналом `loaded`. Параметры реального INDI-устройства
и Capture queue от этих действий не меняются.

## 3. Контракт снимка и задания

Snapshot schema2 содержит геометрические значения и полный угловой горизонт.
Сервер также принимает прежний schema1 без полного контура:

```json
{
  "schema_version": 2,
  "kstars_version": "3.8.6",
  "utc": "2026-11-11T21:00:00Z",
  "altitude_convention": "geometric_unrefracted",
  "location": {"latitude_deg": 60.3, "longitude_deg": 30.315, "elevation_m": 20},
  "focus": {"azimuth_deg": 180, "altitude_deg": 45},
  "artificial_horizon_visible": true,
  "artificial_horizon": {"kind": "KStars_great_circle_v1", "regions": [
    {"name": "Стена", "ceiling": false, "points": [[170, 30], [190, 30]]}
  ]}
}
```

`POST /api/kstars/jobs` принимает `{scene,snapshot}`. Геометрия KStars
подменяет ручные место/дату/центр, сохраняя AGL и настройки модели;
ручная Луна исключается в пользу эфемерид. MSL места сохраняется как
происхождение, а модельная поверхность берётся из DSM, если он включён.
UTC каталога камеры обязан совпадать с UTC снимка.

Я отвергаю неверную схему, неявный пояс времени, NaN и подмену
геометрической высоты рефрагированной. Snapshot и его хеш сохраняются
с заданием. Параметры физического кэша остаются точными.

Автослежение по умолчанию выключено. Смена карты/параметров помечает
результат устаревшим по ключу0,25°/60с; внутри этих квантов небольшие
изменения индикатор не различает. Включённый follow использует стабильность
этого ключа для запуска, но посылает полную фактическую геометрию.
Одновременно панель ведёт одно задание. Отмена проверяется между лучами.
HTTP-тайм-аут 15 с не ограничивает полную длительность расчёта.

Наш D-Bus `org.lightpollution.KStars`, путь `/LightPollution`, использует
session service `org.kde.kstars`. Методы: `snapshotJSON`, `setSceneJSON`,
`calculate`, `statusJSON`, `showEyeView`, `showCameraFITS`,
`savePanelScreenshot`, `saveWindowScreenshot`, `saveEyeScreenshot`,
`saveCameraScreenshot`, `catalogueJSON`, `showEkosExposure`,
`ekosExposureJSON`, `saveEkosScreenshot`. `horizonVisibilityJSON` возвращает
штатную маску для списка направлений; `setVerificationHorizonJSON` разрешён
только в приватном проверочном сеансе и не сохраняет контуры в БД.

## 4. Установка и запуск

Нужны Python≥3.12/uv, CMake/Ninja/C++17, Qt≥6.6, KF≥6.6,
INDI≥2, StellarSolver≥2.6, CFITSIO/cURL, Eigen/GSL/Nova/LibRaw/WCSLIB,
OpenCV≥4.6, XISF и QtKeychain. Это зависимости современного KStars;
установщик не меняет системные пакеты. В обычной системе использую
подготовленный SDK/пакеты своего дистрибутива. Современные KF6 не входят
в исходный комплект Ubuntu24.04; наличие только Qt5 недостаточно.

```bash
uv sync --locked --extra terrain --extra kstars
uv run python integrations/kstars/setup.py --prefix scratch/my-kstars --jobs 1
uv run python integrations/kstars/launch.py --installation scratch/my-kstars \
  --workspace data/eye-model-20261111 --raw-directory data/blackmarble
```

Первая команда установки получает закреплённый исходник KStars3.8.6 Beta
`c46dbb4f0cfe4b8ca190a0c391e975e52a005aa8` с исправленными каталогами и проверяет
SHA-256, применяет совместимый патч, собирает Qt6, устанавливает в выбранный
prefix и подготавливает Tycho-2. Базовые данные/яркие имена взяты из той же
ревизии. Один процесс сборки — безопасное значение по умолчанию; `--jobs 2`
уменьшает время при достаточной памяти. Система KStars не заменяется. Общие Qt-заголовки предварительно компилируются;
`--no-precompiled-headers` отключает это ускорение. Повторная установка
с теми же параметрами переиспользует конфигурацию и сборку; `--reconfigure`
принудительно обновляет CMake.

Если выбираю собственный checkout, добавляю `--source /path/to/kstars`.
Только проверить якоря патча без записи:

```bash
uv run python integrations/kstars/apply_native.py --source /path/to/kstars --check
```

Все якоря проверяются до записи; повторное применение не дублирует меню,
модуль, обработку B−V и точку входа электронного потока Ekos. Несовместимый
checkout отклоняется. Для отдельно размещённого и уже перенесённого SDK
служит `--dependency-root /path/to/root`, содержащий `usr/`. Скрипт не
переписывает его cmake-конфигурации: необходимость переноса абсолютных путей
зависит от самого SDK.

`installation.json` хранит пути, контрольные суммы сборки/данных и Python.
`launch.py` запускает ядро на свободном loopback-порту, ждёт совместимый API,
затем открывает KStars. После закрытия завершает только собственные процессы.
Логи лежат в `prefix/logs`. Запуск использует собственные XDG-каталоги
установки: старые личные файлы не перекрывают проверенный каталог.
Место и контуры в этом профиле задаются штатными средствами KStars и
сохраняются между запусками. Отдельный D-Bus-сеанс не даёт уже запущенному
системному KStars перехватить открытие. Оба наших процесса используют один
сеанс; актуальный адрес/URL на время работы записаны в `prefix/session.json`.
Автоматического копирования личных баз/настроек нет. Нативный D-Bus клиент
должен обращаться к этому же сеансу.

Нативный модуль имеет GPL-2.0-or-later, [COPYING](../integrations/kstars/COPYING).
Права и атрибуция каталога — [DATA_SOURCES](DATA_SOURCES.md).

## 5. Ekos: электронный поток вместо SQM

Кнопка «Экспозиция Ekos» открывает нативное окно рядом с панелью.
Источник — `camera.exports.exposure_bridge` того же результата/хеша профиля.
Штатный `OptimalSubExposureCalculator::calculateSubExposureDetail` получает
своё явное расширение `setExternalSkyElectronRate`; оно подменяет только
скалярную скорость неба. При обычном запуске штатного калькулятора этот
режим выключен и его поведение сохраняется.

Я показываю три скорости b и соответствующие нижние границы выдержки,
верхнюю границу насыщения всего поля и совместимость интервала. Допуск
роста шума изменяется в окне. RN зафиксирован профилем FITS; фиктивные
метки gain0/1 внутри объекта Ekos имеют одинаковый RN и не обозначают
доступные аппаратные gain. Подписи SQM/Bortle в этом окне отсутствуют.
Новый b уже включает спектральный отклик, пиксель и оптику: повторный
множитель QE/f-ratio/filter недопустим. Bayer-камера не объявляется
монохромной реальной камерой: пока этот путь относится к монохромному
сценарию проекта. Прямого редактирования Capture queue/INDI нет.

Старый Qt5/KStars3.6.2 не содержит такого класса. Там остаются FITS и JSON
границ экспозиции; кнопка Ekos выключена. Переносимость современного пути
подтверждаю отдельной сборкой, а не одним условным `#include`.

## 6. Проверка и статус поставки

Автоматическая проверка приватной установки:

```bash
dbus-run-session -- uv run --extra kstars python scripts/check_kstars_native.py \
  --installation scratch/my-kstars --camera --job-timeout 1800 \
  --output data/kstars-qt6-check --url http://127.0.0.1:8766
```

Ядро для этой проверки запускается отдельно на указанном порту. Проверка
сравнивает геометрию/UTC/AGL, живой каталог, FITS Viewer, реальные вычисления
Ekos и полный горизонт с native `ArtificialHorizon::isVisible`, затем
сохраняет снимки настоящих Qt-окон. Контуры теста создаются только в
изолированном сеансе с `LIGHTPOLLUTION_VERIFICATION=1` и не записываются в БД.

Историческая Qt5-проверка:
[2/2 расчёта](../artifacts/camera-model-20261112/native/native-verification.json).
Новая Qt6-поставка проверена фактически: KStars3.8.6 Beta, Qt6.11.1,
KF6.31.0, INDI2.1.9;3/3 задания камеры, штатный FITS Viewer и настоящий
калькулятор Ekos. Повтор17071 записей после поворота сохранил ID/V/B−V/
астрометрию;2054/2054 направлений совпали с ArtificialHorizon. Три поиска
по перестроенному HD-индексу и ожидаемый отказ неверному запросу прошли.
Старый результат после отказа остался устаревшим.

Основной pytest317/317, отдельный wheel94/94 файла,6/6 экспортов,
10/10 FITS checksum. Повторная установка и lifecycle launcher проверены;
свой порт/процессы освобождены, другой backend сохранился.
[Отчёт и снимки](../artifacts/kstars-catalogue-integration-20261112/README.md),
[нативный протокол](../artifacts/kstars-catalogue-integration-20261112/native/native-verification.json).
Это локальное расширение, не принятый upstream-коммит и не проверка
реального оборудования. Новый Qt6-прогон относится к камере;
окно глаза сохраняет прежний отдельный протокол.
