# Численный планировщик 0.6: запуск, архитектура и границы
> Дата создания: 2026-11-11

Актуальное дополнение 0.6: необязательный `SceneSpec.eye` включает
ограниченный скотопический порог и отдельный монохромный PNG. Новых
runtime-зависимостей нет. Планировщик дополняет угловую сетку; изменение
наблюдателя/вида повторно использует ядра переноса. Экспорты eye JSON/CSV,
статусы области и PNG включаются в ZIP при наличии. Без eye старый контракт
сохранён. [Формулы, ограничения и конфигурация](EYE_MODEL.md).
Исторические описания выпусков ниже читаются с учётом этого дополнения.

Физическое продолжение 0.4: численные `background` и `surface` в схеме 2,
те же CLI/HTTP/задания/экспорты, отдельные компоненты и статусы поддержки.
Старые входы без этих полей сохраняют прежний режим.
[Новые параметры и формулы](NATURAL_TWILIGHT_SNOW.md),
[проверки и результаты](../artifacts/natural-twilight-snow-20261111/README.md).

Выполнены шесть технических поставок [плана](OBSERVATION_PLAN.md).
Это локальный сценарный планировщик ясной ночи: место и время, подготовленные
источники, атмосфера, раздельный фон, каталожные звёзды, сравнение и экспорт.
Физические формулы однократного переноса и KS1991 сохранены. Новая модель
глаза, сенсора, снега или цветового восприятия этим выпуском не добавлена.

Версия 0.3 добавила общую нормировку между точками, переносимую наземную
калибровку и спектральный расчёт города/звёзд. Формальная теория —
[PHOTOMETRY_AND_SPECTRA.md](PHOTOMETRY_AND_SPECTRA.md),

## Запуск

Поддерживаемое окружение выпуска: Linux, Python ≥3.12, uv. В корне проекта:

```bash
uv sync --locked
uv run lightpollution serve
```

Открыть `http://127.0.0.1:8765`. По умолчанию рабочие данные находятся в
игнорируемом `data/mvp`, исходные HDF5 — в `data/blackmarble`.
Параметры `--workspace`, `--raw-directory`, `--host`, `--port` задаются явно.
Для нескольких экземпляров нужны разные рабочие папки: в одной папке
работает один управляющий процесс с одним вычислительным работником.

Учебный пример готов без сети и NASA-токена; он явно помечен как искусственный.
Петербургский годовой набор и мадридские месяцы используют настоящие файлы
NASA. Программа сама извлекает область, проверяет QA и подготавливает источники.
Размеры и SHA-256 исходных HDF5 закреплены пакетными манифестами.

```bash
uv run lightpollution datasets
uv run lightpollution example --output data/my-scene.json
uv run lightpollution plan --scene data/my-scene.json \
  --output data/my-result
```

Если NASA-файлов нет, настроить существующий локальный доступ Earthdata через
`BLACKMARBLE_TOKEN_FILE` либо `BLACKMARBLE_TOKEN`. Загрузка выполняется
командой `datasets --download REGION` или при явно выбранном флажке
загрузки в форме. Секрет не вводится в веб-сценарий и не попадает в экспорт.
В запросах `download_missing=false` по умолчанию; подмена набора более новым
или переход с месяца на год не выполняются скрыто.

## Рабочий маршрут

Выбрать регион/период, точку, время с явным смещением UTC и направления.
Атмосферные коэффициенты доступны в форме; опорная длина волны фиксирована
550 нм. Сохранённый `scene.json` можно открыть обратно через форму либо CLI.
Для режима без даты MVP требует явно отключённую Луну; каталог звёзд
не получает фиктивного текущего времени.

Расчёт имеет состояния `queued`, `running`, `completed`, `cancelled`, `error`.
Прогресс относится к завершённым направлениям; подготовка данных может идти
без процентного счётчика. Отмена проверяется между численными блоками,
а не внутри операции чтения HDF5 или одного интеграла. Завершённые лучи
сохраняются для повтора. После остановки сервера незавершённые задания
помечаются прерванными, а не успешными.

Экспорт содержит `scene.json` схемы 2, развёрнутые параметры, `result.json`,
`observation.json`, таблицы фона/звёзд и ZIP. Старые сцены схемы 1 остаются
доступны через `observe`; служебный `input_scene` внутри нового наблюдения
не является самостоятельным сценарием со ссылками на физические файлы.
Для повторения нового запуска используется именно `scene.json` схемы 2.

## Что показывается

- Городской, лунный и постоянный естественный фон в общей шкале `B/Bref`;
  `μref=22` V mag/arcsec² задаёт единицу сравнения.
- Сценарные V-величины суммы, геометрия Солнца/Луны, фаза и маски применимости.
- Положение и ослабленные V-потоки каталожных звёзд; это не список звёзд,
  достоверно обнаружимых невооружённым глазом.
- QA-покрытие с числителем/знаменателем, период источников и происхождение
  коэффициентов. Спутниковый период не обещает реальное освещение будущего часа.

Сравнение допускается при общей региональной нормировке источников, одном
коэффициенте мощности, полосе и модели. Разные точки, даты, AOD и месяцы
допускаются. В спектральном режиме можно менять текущую смесь ламп при
фиксированной мощности. Серое и спектральное поля имеют разные шкалы отклика;
их нельзя сравнивать одной старой калибровкой. Сценарное межточечное сравнение
не является независимой проверкой реальной яркости этих мест.

Опора находится в фиксированной точке региона; JSON допускает
`anchor_observer`. Подготовка общей маски/знаменателя не зависит от наблюдателя.
Ближние пиксели исключаются после нормировки, их мощность не восстанавливается.

## Калибровка и спектры

`fit-photometry --dataset FILE --output FILE` принимает ясные безлунные
измерения Johnson-V и ссылки на экспортированные `result.json`. Требуются
непересекающиеся обучающие и контрольные ночи, источник QA, UTC, станция
и направление. [Реальный пример](../artifacts/photometry-spectra-20261111/ground-dataset.json).
`plan --calibration FILE` добавляет документ в сценарий; в форме есть загрузка
калибровки. Её область и контрольный хеш проверяются, в том числе после
перехода чисел JSON `22.0` ↔ `22` в браузере.

```bash
uv run lightpollution example --spectral --output data/spectral-scene.json
uv run lightpollution plan --scene data/spectral-scene.json --output data/spectral-result
uv run lightpollution spectral-library
```

Спектральный режим включается в форме или объектом `spectrum` внутри сцены:

```json
{"mix":{"HP1":1},"reference_mix":{"LED-B3":1},"angstrom_exponent":1.3,"stars":"catalogue_continuum"}
```

Доли относятся к излучённой мощности в принятом интервале, не к числу фонарей
или люменам. Опора LED-B3 сохраняется при смене текущей смеси.
`measured_only` отключает континуумные формы звёзд по B−V. Полный спектр
города и несколько звёздных примеров находятся в `result.json`; доступные
звёздные полосовые потоки и рецепты — в `stars.csv`.
Спектры Луны/естественного фона пока отсутствуют.

## Общий масштаб при изменении атмосферы

Старый численный режим может задавать зенит каждого поля отдельно. Новый
планировщик фиксирует **один коэффициент источников** по опорному месяцу
и опорной атмосфере, затем переносит его на другие условия:

```text
qanchor = 10^[−0.4(μanchor−22)]
Csource = qanchor / Rreference(zenith; θreference)
qcity,m(ω; θ) = Csource × Rm(ω; θ)
```

`R` — отклик прежнего решателя с сохранённым месячным отношением мощности;
`θ` — текущие атмосферные параметры. При смене AOD зенит не возвращается
принудительно к прежней яркости. Опорный отклик всегда использует стандартный
численный профиль. Происхождение масштаба MVP — `scenario`, полевая точность
не удостоверяется. Историческая настройка AstMon на высоте 650 м сюда
автоматически не переносится.

## Высоты и область применимости

Ввод высоты 0–100 м — AGL. Без `terrain` это общая сферическая поверхность
источников. С `terrain` к AGL добавляется высота DSM, и источники поднимаются
на тот же DSM; атмосферные пути начинаются с этих абсолютных высот.
При `near_field` AGL ≥0,5 м. Высота места KStars сохраняется отдельно и
не подменяет AGL. Система датумов, приближения и ограничения:
[TOPOGRAPHY_AND_NEAR_FIELD.md](TOPOGRAPHY_AND_NEAR_FIELD.md).

Количественные направления MVP: высота 10–90°, ясная астрономическая ночь,
разделение с Луной ≥10°. Сумерки отклоняются до тяжёлого расчёта. Возможное
затмение и ближняя зона Луны маскируются. Звёзды ниже сетки 10° не входят
в новую таблицу, их количество вне покрытия указывается в метаданных.

Вода и источники за границами региона исключены. Без `near_field` сохраняется
прежнее исключение ближних 3 км; с ним конечные ячейки включены. Для месячных
пар требуется общая маска минимум 80% опорной суши до ближних исключений.
Нулевой QA июля Петербурга приводит к отказу, а не к тёмной картинке.
Сценарный снег, ограниченные сумерки и слой естественного фона реализованы
в 0.4. В 0.5 добавлены DSM и выборочное заслонение; отдельные здания/лампы,
многократное рассеяние и подробные карты естественного фона остаются расширениями.

## Модули и контракты

`domain/` содержит `SceneSpec`, `SkyField`, `StarFluxTable`, `RunResult`,
ресурсы и структурированные ошибки. Принятый запрос хранится как отдельный
неизменяемый JSON-снимок. `models/observation.py` считает сцену по переданным
массивам и каталогу; файлов/HTTP там нет. `TransferSolver` позволяет заменить
интегратор, сохранив выходной контракт. Прежние `physics.py`, `sources.py`
сохраняют проверенные формулы и публичные импорты.

`application/Planner` связывает подготовку источников, опорный масштаб,
перенос и наблюдение. `adapters/` читает NASA, NPZ, каталог и атомарные файлы.
`interfaces/` содержит веб-форму и команды, которые обращаются к одному
прикладному сценарию. Старые `scene.py` и `cli.run_simulation` совместимы
через обёртки; массового изменения формул вместе с переносом не было.

Фон хранится на единицу телесного угла, звёздный поток — отдельно относительно
V=0. Нет скрытого превращения этих величин в электроны камеры. Без даты
отсутствуют и звёздные capabilities. `eye_detection`, `camera_electrons`,
`validated_display` недоступны. При включённых спектрах доступны
`city_spectral_radiance` и `spectral_band_responses`; полный спектр суммы
пока недоступен. Источники/профили и их SHA входят в ключи спектральных сцен.

Кэш разделён на проверенные карты, общую месячную область, отдельные лучи
и итоговую сцену. Физический ключ включает массивы источников, точку,
атмосферу, профиль, версию и хеши кода физики. Сцена дополнительно зависит
от времени, каталога и фотометрии. Изменение CSS не пересчитывает перенос;
изменение AOD пересчитывает текущие лучи, сохраняя опорный коэффициент.
Файлы публикуются атомарно, контрольные суммы защищают от случайной порчи.

## API локального приложения

`GET /api/catalogue`, `POST /api/jobs`, `GET /api/jobs/{id}`,
`POST /api/jobs/{id}/cancel`, `GET /api/jobs/{id}/result`,
`GET /api/jobs/{id}/export/{name}`, `POST /api/compare`.
Дополнительно: `GET /api/spectral-library`, `POST /api/photometry/fit`;
у второго `cases` содержит идентификаторы завершённых заданий.
Экспорт доступен только для завершённого задания и перечисленных файлов.
Коды отказов различают сумерки, плохое покрытие, отсутствующие данные,
несовместимую шкалу и прерванное задание. Один сервер допускает восемь
ожидающих/работающих заданий; численный работник один.
