# Независимая проверка невооружённого глаза
> Дата создания: 2026-11-11

## Статус и назначение

0.8 реализует хранение профилей, импорт, проверку разделения данных и
оценку диагностического F. Реальных наблюдений пока нет. Синтетические
метки из unit-тестов не входят в статистику людей или наблюдательных ночей.
Ни автоматическая валидация цвета, ни эксперимент с участниками не выполнены.

## Теория → проблема → решение

**Теория.** В Crumey `E_threshold=F·T(B)`; положим
`b=E_star/T(B)=q_saved·F_saved`. Для нового F предсказание обнаружения
`b/F≥1`. F безразмерен; он не меняет ни поток звезды, ни фон, ни C города.

**Проблема.** Наблюдатель, адаптация, ошибки яркости неба и прозрачности
могут давать похожее изменение порога. Если настроить F по контрольным
ответам или той же ночи, качество будет завышено. Цветовое впечатление
не определяется одним ответом «видел».

**Решение.** Подбирается только F в [0,5;10] по calibration-записям данного
наблюдателя. Цель — максимальная balanced accuracy, среднее чувствительности
и специфичности, чтобы многочисленные невидимые звёзды не подавляли видимые.
Нужны обе категории. Перебираются точки изменения порога, промежутки между
ними и номинальный F=2. При равенстве выбирается ближайший в log F к медиане
прежних F. Это оценка порогового классификатора, не регрессия физиологии.
Не оцениваются доверительные интервалы по независимым звёздам: внутри ночи
ответы связаны. Размер будущей выборки следует определять по числу ночей и
наблюдателей; для интервалов потребуется кластерный bootstrap по ночам.

Calibration/validation не могут делить ни night_id, ни SHA-256 исходного
расчёта, даже для разных наблюдателей. Итоговые TP/TN/FP/FN, точность,
чувствительность, специфичность и balanced accuracy записываются вместе
со знаменателями seen/not_seen/records, отдельно по наблюдателям и ночам.
Если в контроле только одна категория, balanced accuracy неизвестна.
Если обучения недостаточно, F остаётся null, проверки не объявляются точными.
Настроенный F может поглотить ошибку фона и атмосферы — это нужно проверять
параллельным независимым измерением неба, а не трактовать как свойство глаза.

## Сбор реальных записей

1. До просмотра ответа модели зафиксировать точку, UTC, высоту, модель
   атмосферы и горизонт. Ясное небо, Солнце ниже −18°, Луна под горизонтом,
   отсутствие прямых фонарей — действующая область модели глаза.
2. Зафиксировать анонимный observer_id, коррекцию зрения, длительность
   адаптации и способ наблюдения. Для пилота ориентир — не менее 30 минут
   без яркого экрана; импорт отклоняет условия менее 20 минут. Это лишь
   протокольный фильтр, не доказательство полной адаптации конкретного глаза.
3. Заранее выбрать звёзды разных q, включая ответы «не видел», перемешать
   порядок, использовать одинаковое время поиска. Названия созвездий и
   результаты модели могут создавать ожидание; протокол должен это учитывать.
4. Записать seen и при желании отдельную colour_label. Не подменять ответ
   яркой фотографией или догадкой по каталогу. Для повторных попыток создавать
   отдельный случай/результат с собственным протоколом, не дублировать строку.
5. Заранее отделить ночи для обучения от контрольных, включить несколько
   независимых ночей и наблюдателей. Один подготовленный night_id не считается
   подтверждением переносимости на другой сезон, место или спектр освещения.
6. Для изображения измерить белую/чёрную яркость, физическую ширину поля и
   расстояние просмотра, отметить освещение помещения, профиль ОС и масштаб
   приложения. Для строгой LMS-модели нужны спектры первичных цветов.
   PNG, открытый в Telegram без этих условий, остаётся иллюстрацией.

Инструмент не проводит эксперимент и не удостоверяет подлинность переданных
записей. Публиковать следует обезличенные агрегаты; рабочие персональные
данные не добавляются в Git автоматически.

## Формат и импорт

Начальный [пустой шаблон](../artifacts/eye-colour-20261111/observation-template.json)
валиден и даёт status=prepared_not_observed, observers=0, nights=0.
После сбора документ имеет вид ниже. Указанные строки — **структурный
пример с заменяемыми значениями**, не данные наблюдения:

```json
{
  "schema_version": 1,
  "kind": "eye_observations",
  "cases": [{
    "id": "site-night-a",
    "night_id": "site-2026-11-11",
    "result_path": "relative/path/to/result.json",
    "result_sha256": "REPLACE_WITH_ACTUAL_LOWERCASE_SHA256_OF_RESULT_FILE",
    "conditions": {
      "clouds": "clear",
      "adaptation_minutes": 30,
      "direct_lamps_visible": false
    }
  }],
  "observations": [{
    "case_id": "site-night-a", "observer_id": "anonymous-001",
    "hr": 7001, "seen": true, "split": "calibration", "colour_label": null
  }]
}
```

`result_path` разрешается относительно файла набора. Скрипт проверяет SHA-256
байтов, затем ищет HR в физическом eye-результате. Неподдерживаемые моделью
строки/условия исключаются с подсчётом; они не превращаются в «не видел».
Дубликаты observer/case/star, нестрогие boolean и утечка ночей вызывают ошибку.
Цвета: null, white, red, orange, yellow, blue, uncertain. Эти метки сохраняют
ответы, но ещё не оцениваются как проверенная классификация цвета.

```bash
uv run python scripts/audit_eye_observations.py \
  artifacts/eye-colour-20261111/observation-template.json \
  --output artifacts/eye-colour-20261111/observation-status.json
```

Сначала нужны реальные наблюдения и измерения; затем сравнение ошибок,
чувствительность к угловому диаметру, условиям и профилям, и только после
этого решение о калиброванном цвете, бликах и динамической адаптации.
